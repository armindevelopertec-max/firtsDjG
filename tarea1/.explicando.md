# Guía Técnica Avanzada: Flujo de Datos y Arquitectura del Proyecto

Este documento proporciona un desglose exhaustivo de los componentes técnicos, la interacción entre servicios y el ciclo de vida de los datos dentro del ecosistema del proyecto.

---

## 1. Capa de Virtualización y Red (Docker Stack)

El proyecto utiliza una arquitectura de microservicios orquestada. No es simplemente "correr un script", sino levantar un entorno de red definido por software.

### 1.1 Resolución de Nombres y Networking
En `docker-compose.yml`, el servicio de base de datos se denomina `db`. 
- **Mecánica**: Docker implementa un servidor DNS interno. Cuando la aplicación Django intenta conectarse al host `db` (configurado en `settings.py`), el DNS de Docker traduce ese nombre a la IP interna del contenedor de MariaDB dentro de la red `django_net`.
- **Aislamiento**: Solo los servicios en `django_net` pueden comunicarse entre sí por sus nombres de servicio.

### 1.2 El Driver de Conexión (C-Level Interaction)
En el `Dockerfile`, la línea:
```dockerfile
RUN apt-get update && apt-get install -y default-libmysqlclient-dev build-essential pkg-config
```
Es fundamental. Instala las librerías de desarrollo de MariaDB en el sistema operativo del contenedor. Esto permite que el paquete de Python `mysqlclient` compile extensiones en C, lo que garantiza una comunicación de alto rendimiento y baja latencia con el servidor de base de datos.

## 2. Bootstrapping y Configuración de Django

### 2.1 El Punto de Entrada (WSGI)
Cuando se ejecuta `python manage.py runserver`, Django inicia a través de un objeto de aplicación WSGI (Web Server Gateway Interface).
- Archivo clave: `tarea1/wsgi.py`.
- Función: Actúa como el puente entre el servidor web (en este caso, el servidor de desarrollo de Django) y el código de la aplicación.

### 2.2 Inyección de Configuración
En `settings.py`, la variable `DATABASES` inyecta las credenciales:
```python
'HOST': 'db', # Resuelto por el DNS de Docker
'PORT': '3306', # Puerto interno del contenedor (no el 3307 mapeado al host)
```
Es importante notar que mientras el host ve la DB en el puerto `3307`, la aplicación Django habla directamente con el puerto nativo `3306` dentro de la red virtual.

## 3. Capa de Persistencia (ORM & Migrations)

### 3.1 El Motor ORM (Object-Relational Mapping)
El modelo `Operacion` en `operacion/models.py` abstrae la complejidad de SQL.
- **Definición de Esquema**:
  ```python
  numero1 = models.FloatField() # Se traduce a DOUBLE en MariaDB
  fecha = models.DateTimeField(auto_now_add=True) # Genera un TIMESTAMP automático
  ```
- **Migraciones**: Django rastrea cambios en los modelos. Al ejecutar `python manage.py makemigrations` y `migrate`, el framework genera y ejecuta sentencias `CREATE TABLE` o `ALTER TABLE` en MariaDB automáticamente.

## 4. Ciclo de Procesamiento de Peticiones (Request Lifecycle)

### 4.1 Capa de Middleware (Seguridad y Sesión)
Antes de que una petición llegue a la vista `suma`, pasa por una serie de filtros en `settings.py`:
1. `SecurityMiddleware`: Fuerza conexiones seguras.
2. `SessionMiddleware`: Gestiona el estado del usuario.
3. `CsrfViewMiddleware`: Protege contra ataques de falsificación de petición en sitios cruzados (esencial para el formulario de suma).

### 4.2 Lógica de la Vista (`operacion/views.py`)
La función `suma(request)` es una **Vista Basada en Funciones (FBV)** que maneja múltiples estados:

#### Estado A: Acceso Inicial (GET)
- La petición llega con `request.method == "GET"`.
- Se salta el bloque `if`.
- Ejecuta `Operacion.objects.all().order_by('-fecha')[:5]`.
- El ORM genera un SQL similar a: `SELECT * FROM operacion_operacion ORDER BY fecha DESC LIMIT 5;`.

#### Estado B: Procesamiento de Datos (POST)
- Al presionar "Calcular", se envía un `POST`.
- **Validación Robusta**:
  ```python
  try:
      n1 = float(request.POST.get("num1", 0)) # Casting de String a Float
      resultado = n1 + n2
      Operacion.objects.create(...) # Commit atómico a la base de datos
  except ValueError:
      resultado = "Error: Ingrese números válidos" # Manejo de excepciones para evitar el crash (500)
  ```

## 5. Capa de Presentación (Template Engine)

El renderizado se realiza en el servidor (Server-Side Rendering - SSR).
- **Archivo**: `operacion/templates/operacion/suma.html`.
- **Contexto**: El diccionario pasado en `render(...)` permite que el motor de plantillas de Django inyecte variables dinámicas.
- **Bucle de Historial**:
  ```html
  {% for op in historial %}
      <li>{{ op.numero1 }} + {{ op.numero2 }} = {{ op.resultado }}</li>
  {% endfor %}
  ```
  Esto se traduce en HTML puro antes de ser enviado al navegador, asegurando que el cliente reciba la información final lista para visualizar.

---

## 6. Flujo de Control Resumido

1.  **Navegador**: Envía `POST /suma/`.
2.  **Docker Net**: Redirige al contenedor `web`.
3.  **Django Middleware**: Valida el Token CSRF.
4.  **URL Resolver**: Mapea `/suma/` a `views.suma`.
5.  **View Logic**: Calcula el resultado y llama al **ORM Manager**.
6.  **Database Driver**: Ejecuta `INSERT` en MariaDB.
7.  **Template Engine**: Genera el HTML con el nuevo historial.
8.  **Navegador**: Recibe y muestra la página actualizada.
